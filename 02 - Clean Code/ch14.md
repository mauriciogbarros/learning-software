# 14. Testing Disciplines


---

## Discipline 1: Test-Driven Development (TDD)
### The three laws of TDD
- Write no production code until you have first written a test that fails due to the lack of that production code.
  - If you can write the production code, you can also write the code that tests the production code.
- Write no more of a test than is sufficient to fail, or fail to compile. Resolve the failure by writing some production code.
  - You will often be unable to write more than one line of a test before having to switch over to writing production code.
- Write no more production code than will resolve the currently failing test. Once the test passes, write more test code.
- The cycle
  - You write a line of test code, but it doesn't compile (of course).
  - You write a line of production code that makes the test compile.
  - You write another line of test code that doesn't compile.
  - You write another line or two of production code that makes the test compile.
  - You write another line or two of test code that compiles, but fails an assertion.
  - You write another line or two of production code that passes the assertion.

---

## Discipline 2: Test && Commit || Revert (TCR)
- Code that passes tests should be immediately committed, and code that fails tests should be immediately reverted.
  - This is generally enforced with a script that runs the tests whenever source files are saved and automatically executes the commit or revert based on the test results.
  - The programmer can write as much test and production code as they like, but they are liable to lose what they wrote if they have not written tests that pass.

---

## Discpline 3: Small Bundles
- Programmers write a small bundle of code and tests to achieve a certain result.
  - They might write the code first, they might write the tests first, they might intersperse the writing of the code and the tests.
  - But they will conclude with that small bundle having high test coverage and all tests passing.

---

## Design
- Testing discipline are not intended to supplant strategic thinking.
- Months of strategic planning, without any coding, is suicide. Coding without any strategic planning is equally suicida.
- These disciplines test the design of the code by imposing the viewpoint of users - after all, the tests are a kind of user.

---

## Discipline
- Disciplines like these should be taken seriously; but they are not universally applicable and should not be followed blindly.

### Tedious, boring, and slow
#### Debugging
- Following one these disciplines (TDD) has reduced debug times.

#### Documentation
- The tests are the code examples for the whole system.
- Each one of those tests are isolated from all the others.
- The tests produced are a document that describes the low-level design of the system.
- They are not high-level documentation.

#### Reliability
- When the tests pass, you know with a high degree of confidence that the system works as it should.

#### Design
- By writing the test along with the code, you are automatically deisgning every module to be easy to test.
- A module that is easy to test is decoupled.

#### Reprise
- Significantly reduce debugging time.
- Create a stream of nearly perfect low-level documentation.
- Create a test suite that you trust so much that you can deploy when it passes.
- Create a system with a less coupled design.

### The angel and the devil
#### Muzzling the devil
- If you have a test suite, and if you trust that test suite, and if that test suite runs quickly, then you will clean the code.
  - You will, because cleaning the code is virtually risk free.

### Complications and loopholes
- There are situations where writing tests is either impossible or at least impractical.
- Seasoned developers will design their systems such that those untestable stretches of code are very thin.
- When faced with areas of the system that impractical to test, try to make those areas as small and simple as possible, and protect the rest of the system from them.

### Costs and repercussions
- The sheer bulk of the test, which can rival the size of the production code itself, can present a daunting management problem.

---

## Keeping Tests Clean
- Test code is just as important as production code.
  - It is not a second-class citizen.
  - It requires thought, design, and care.
  - It must be kept as clean as production code.

---

## Tests Enable the -ilities
- It is tests that keep code flexible, maintainable, and reusable.
  - If you have tests, you do not fear improving the code.
  - Without tests, every change is possible bug.
- Having an automated suite of tests that cover the production code is they key to keeping your design and architecture as clean as possible.
  - Tests enable all -ilities, becuase tests enable change.
