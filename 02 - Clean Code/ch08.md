# 8. Function Heuristics
## Function Arguments
- Every argument you add to a function signature makes that function harder to understand.
- If I need to pass more than three arguments into a function, I try to find a way to group them.
  - Put them in an object.
- One of the simplest ways to reduce argument lists is to create fields in the current class to hold the values that we would otherwise pass as arguments.
  - One of the reasons that OO is a powerful tools is that it allows us to create contexts that allow functions to communicate without passing a lot of arguments.

### Variadic arguments
```java
public String format(String format, Object... args)
```
- It is same to assume that this function really just takes two arguments:
  - The `format`
  - The array of `Object`s named `args`

### More than three?
- Risk of getting the order wrong.

### Keyword arguments
```csharp
createRental(movie: m, daysRented: 3)
```
- On occasion, pass more than three.

### Flag arguments
- Ugly
  - Passing a `boolean` into a function is generally careless.
  - Loudly proclaims that the function does more than one thing.
- The solution, where possible, is to split the function into two functions: one that does the `true` case and one that does the `false` case.

### Output arguments
- Try to avoid.
- People expect data to go into functions through the arguments and out from functions through the return value.
- Much of the need for output arguments disappears in OO languages becauase the object itself can act as the output of its methods.

### Error codes
- So long as this convention is applied narrowly and consistently, it is a reasonable convention; especially in a language like Go that does not have exceptions.

## Command Query Separation
- Under the CQS convention, functions either do something or answer something, but not both.
  - Either a function is a command that creates a side effect (i.e., it changes the state of the system), or
  - It is a query that returns some information.
- For example:

```java
public boolean set(String attribute, String value);
```
  - This function sets the value of a named attribute and returns `true` if is successful and `false` if no such attribute exists.
  - Leads to odd statements: `if (set("username", "unclebob"))...`

- Possible solution

```java
if (attributeExists("username")) {
	setAttribute("username", "unclebob");
	...
}
```

- There are situations where CQS is impractical or just inconvenient.
  - `int top = stack.pop();`

- Is there a cost to violating CQS? Yes: concurrency.
  - If the `pop` function is not made atomic with the proper use of semaphores or locks, then it could be possible for a race condition to cause the top of the stack to be returned to two different threads before that object was properly removed from the stack.

## Prefer Exceptions to Returning Error Codes
- In most of our modern languages, they are a reliable way to transmit error information up the calling stack.
- In older languages, most notably C++, that reliability is not guaranteed.
- And in some languages, like Go, exceptions just don't exist.

### Caveat emptor
- Returning error codes from command functions is a subtle violation of CQS

### Extract `try/catch` blocks
- `try/catch` blocks are ugly in their own right.
  - They confuse the struct of the code and mix error processing with normal processing.
  - It is better to extract the bodies of the `try` and `catch` blocks out into functions of their own.

### Error handling is one thing
- A function that handles errors should do nothing else.

### The dependency magnet of error codes
- It's a good idea to know how your build system works, and whether dependency magnets will cause thrashing of the build and require redeployment.

## DRY: Don't Repeat Yourself
### Simple repeated code
- Given `L` lines of code repeated over and over in `P` different places.
  - `L = 2` and `P = 2`, doesn't make sense to turn them into a function.
  - If `L` is likely to grow and `P = 2`, it might be a little inconvenient, but it's a minor issue.
  - If `P` is large, even if `L` is small, it is probably best to extract the duplication into a single, nicely named function.

### Similar code
- Often we will find repeated snippets of code that are not perfectly duplicated.
  - They may differ by one or two constants or variables.
  - Such snippets often tend to have a larger `L`, and so should be extracted.

### Loop duplication
- The popular way to eliminate this duplication is to use a lambda.
- Older, and sometimes better options are to use the Command pattern, the Strategy pattern, or the TemplateMethod pattern.

### Accidental versus essential duplication
- Sometimes two stretches are code appear to be duplicates, when in fact they are not.
- If two similar stretches of code are in two modules that are responsible to different actos, then they are likely to evolve separately as those actors ask for different changes.
  - If you extract them into a common function, then you are likely to break the system for one actor while you try to satisfy the other.
- If two similar stretches of code are in modules responsible to the same actor, then they are likely to evolve together.
  - If you forget to change one of those stretches, then you will break the system for that actor.

## Side Effects
- Any state change that outlives the function, even if that state change is the primary intent of the function.
  - A function with a side effect is impure.
- For example: `stack.pop()` removes the first item on the top of the `stack`, then it leaves that `stack` in an altered state; the alteration of that state is a side effect.
- Side effects introduce an insidious form of coupling called *temporal coupling* - coupling in time.
  - A statement with a side effect separates the code above it from the code below it with a change of state.
  - That change of state means that the order of those lines of code must be preserved.
- Side effect functions often come in paris, like `open/close`, `seize/release`, or `malloc/free`.
  - One creates the side effect and the other undoes it.

### We are bad at this
- Garbage collection has been added to our languages to cure the fact that we are just so bloody awful at balancing `malloc` with `free`.
- Temporal couplings created by side effects are at the root of all concurrent update problems, all reentrancy problems, all race conditions, and nearly all initializationand finalization problems.

### Functional languages
- You can avoid a lot of side effects by using a functional language.
  - It is still possible to create temporal couplings with functional languages - but most functional languages have facilities that make it very obvious when you are creating them.
- Functional languages allow names to be assigned to values.
  - While you may be able to reassign then name, you cannot overwrite the value.

### Object-oriented languages
- The facilities of most OOPLs provide a handy way to hide side effects behind encapsulation boundaries, thus preventing temporal couplings from leaking out into the application at large.

## Structured Programming
- All programs should be written using only three control structures: sequence, selection, and iteration.
- Dijkstra said that all programs should be ordered as recursively applied units with a single entry and a single exit.

### Sequence
- A sequence is two (or more) units that are executed one after the other.
  - Each such unit has a single entry at the top and a single exit at the bottom.

### Selection
- A selection is a boolean predicate that selects one of two units below it.

### Iteration
- An interation is a predicate that executes the unit below it until the predicate is false.

## Conclusion
- Every system is built from a domain-specific language designed by the programmers to describe that system.
  - Functions are the verbs of that language, and contexts are the nouns.
- Master programmers think of systems as stories to be told rather than programs to be written.
