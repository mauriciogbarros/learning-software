# 16 Acceptance Testing

- Out of all the disciplines of clean code, this is the one that programmers have the least control over.
  - Fulfilling this discipline requires the participation of the business and, unfortunately, many businesses have proven unwilling to properly engage.
- How do you when a system is ready to deploy?
  - Typically, the QA folks run a rather large battery of manual tests that walk through the various behaviors of the system until they are convinced that the system behaves as specified.
- This means that the true requirements of the system are those tests.

---

## The acceptance testing discipline

- The discipline of acceptance testing recognizes this simple fact and recommends that all requirements be specified as tests.
  - Those tests should be written by business analysts (BA) and QA on a feature-by-feature basis, shortly before each feature is implemented.
  - QA is not responsible for running those tests, it is left to the programmers who will very likely automate those tests.
- The specifications of software behavior is always a simple function of specifying input data, the action to perform, and expected output data.
  - this is the well-known AAA pattern, or the Given-When-Then discipline of behavior-driven development (BDD).

```text
Given a page with the wiki test: !1 header
When that page is rendered.
Then the page will contain: <h1>header</h1>
```

### The Discipline

- BA focuses on the happy scenarios, while QA focuses on exploring the myriad of ways that the system can fail.
- BA and QA provide the programmers with these tests, and the programmers automate them in a manner that keeps BA and QA engaged.
- These tests become the definition of done.
- Huge responsibility on BA and QA.
  - The tests that they write must be full specifications of the features being tested.
- In some cases, BA and QA may not be accustomed to writing such formal and detailed documents.
  - In that case, the programmers may wish to write the acceptance tests with guidance from BA and QA.
  - The intermediate goal is to create tests that BA and QA can read and bless.
  - The ultimate goal is to get BA and QA comfortable enough to write the tests.

### The Continuous Build

- Once an acceptance test passes, it goes into the suit of tests that is run doing the continuous build.
  - The continuous build is an automated procedure that runs every time a programmer checks code into the source code control system.
  - The state of the continuous build is something everyone should be continously aware of.

---

## Conclusion

- Acceptance testing is one of the weakest aspects of software development in the first half of the twenty-first century.
- The businesses and the developers must learn to collaborate to create a lanuguage and a procedure to allow requirements to be formally specified by BA and QA and that allow programmers to quickly verify that those requirements have been satisfied.
- The advent of AI makes this need doubly important.
