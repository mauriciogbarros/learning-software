# 18. Simple Design

- The best design for a system is the simplest design that supports all the required features of that system while simultaneously affording the greatest flexibility for change.
  - Simple means untangled; and untangling things is hard.
- A simple design is a design in which high-level policies are ignorant of low-level details.
- The primary means for creating this separation and isolation is *abstraction*.
- One of the physical means we employ for this abstraction is polymorphism.
  - We arrange high-level policies to use polymorphic interfaces to manage the low-level details.
  - Then, we arrange the low-level details as implementations of those polymorphic interfaces.
  - This is the essence of the Dependency Inversion Principle (DIP).

---

## YAGNI

- "You aren't gonna need it."
- Be sure to count the costs and advantages on both sides of the argument.
  - Make sure you ask yourself the question: *What if I'm not gonna need it?*
- If you have a good suite of tests and you are skilled at the discipline of refactoring, then the cost of adding a new feature and updating the design to support that new feature will very often be smaller than the cost of implementing and maintaining all the hooks you might need one day.

## Covered by Tests

- The only reasonable coverage goal is 100%

### An Asymptotic Goal

- Think of 100% as an asymptotic goal.

### Design?

- Testable code is decoupled code.

---

## Maximize Expression

- The structure of the algorithm is easy to see, the code is expressive and simple.

### The Underlying Abstraction

- Not just about nice names for functions and variables, also the separation of levels and the exposition of the underlying abstraction.
- A software system is expressive if each line of code, each function, and each module lives in a well-defined partition that clearly depicts the level of the code and its place in the overall abstraction.

### Tests: The Other Half of the Problem

- The system (code and tests) must communicate everything you want to communicate.
- Every test you write, especially if those tests are isolated and decoupled, is a demonstration of how the production code is intended to be used.

---

## Minimize Duplication

- Duplication leads to fragility.
- The duplications of the traversal code can be eliminated by encapsulating it in one place, and using lambdas, Command objects, the Strategy pattern, or even the Template Method pattern to pass the necessary operations into the traversal.

### Accidental Duplication

- There are situations in which two stretches of code may be very similar, even identical, but will change for very different reasons.
  - Accidental duplicates should not be eliminated.

---

## Minimize Size

- A simple design is composed of as few simple elements as possible without compromising test coverage and expression.

---

## Simple Design

- The principles of design can be reduced to coverage, expression, singularization, and reduction.
