# 2. A Pragmatic Approach

## Topic 8 - The Essence of Good Design

> Tip 14: Good design is easier to change than bad design

- A thing is well designed if it adapts to the people who use it.
  - For code, that means it must adapt by changing.
  - ETC principle: Easier to Change
	- Every design principle out there is a special case of ETC.
	- Decoupling, naming, ...

- ETC Is a value, not a rule
  - Values are things that help you make decisions.
  - ETC is a guide, helping you choose between paths.
  - Ask yourself: "Did the thing I just did make the overall system easier or harder to change?"
  - Another approach: try to make what you write replaceable.
  - Another approach: treat this as a way to develop instincts.

## Topic 9 - DRY - The evils of duplication

- Knowledge isn't stable, it changes - often rapidly.
  - Your understanding of a requirement
  - A change in regulation
  - Some business logic gets outdated.
  - We spend a large part of our time in maintenance mode, reorganizing and reexpressing the knowledge in our systems.

- When us programmers perform maintenance, we have to find and change the representations of things.
  - The problem is that it's easy to duplicate knowledge in the specifications, processes, and programs.
  - Maintenance nightmare

- Every price of knowledge must have a single, unambiguous, authoritative representation within a system.

> Tip 15: DRY - Don't Repeat Yourself

- DRY is more than code
  - It is about duplication of knowledge, of intent.
  - It is about expressing the same thing in two different places, possibly in two totally different ways.

- Not all code duplication is knowledge duplication
  - For example, two functions can validate separate things that must happen to have the same rules.

- Duplication in documentation
  - The intent of a function can be given twice: once in the comment and again in the code.
  - If changes are made, both need to be updated.

- DRY violations in Data

- Representational duplication

- Duplication across internal APIs

- Duplication with Data Sources

- Inter-developer duplication

>Tip 16: Make it easy to reuse.

## Topic 10 - Orthogonality

- A term borrowed from geometry.
- In computing, the term has come to signify a kind of independence or decoupling.
- Two or more things are orthogonal if changes in one do not affect any of the others.
  - The database code will be orthogonal to the user interface.

### A Non-orthogonal system
- Helicopter controls are decidedly not orthogonal.

### Benefits of Orthogonality
- Non-orthogonal systems are inherently more complex to change and control.
  - When components of any system are highly independent, there is no such thing as a local fix.

>Tip 17: Eliminate effects between unrelated things

- Design components that are self-contained
  - Independent
  - With a single, well-defined purpose

- Major benefits
  - Gain productivity
    - Changes are localized, development time and testing are reduced.
    - Promotes reuse, by having specific, well-defined responsibilities, they can be combined with new components in new ways.
    - More functionality per unit effort.
  - Reduce risk
    - Diseased sections of code are isolated.
    - The resulting system is less fragile.
    - The resulting system is better tested.
    - Less dependent on third parties.
  - Design

### Design
- Systems should be composed of a set of cooperating modules, each of which implements functionality independent of the others.
  - Sometimes components are organized into layers, each providing a level of abstraction.
  - Each layer uses only the abstractions provided by the layers below it.

- Easy test for orthogonal design:
  - If I dramatically change the requirements behind a particular function, how many modules are affected?
  - In an orthogonal system, the system should be "one."

- Also ask how decoupled your design is from changes in the real world.

### Toolkits and Libraries
- Be careful to preserve the orthogonality of your system as you introduce third-party toolkits and libraries.

- Decorator Pattern: adding functionality to things without changing them.

### Coding
- Keep your code decoupled: write shy code - modules that don't reveal anything unnecessary to other modules and that don't rely on other modules implementations.
- Avoid global data
- The Singleton pattern is a way of ensuring that there is only one instance of an object of a particular class.
- Avoid similar functions => Strategy pattern

### Testing
- Writing unit tests is itself an interesting test of orthogonality.

- Bug fixing is also a good time to assess the orthogonality of the system as a whole.
  - When you come across a problem, assess how localized the fix is.

### Documentation
- Orthogonality also applies to documentation.

### Living with Orthogonality
- Orthogonality is closely related to the **DRY principle**

## Topic 11 - Reversibility
- There is always more than one way to implement something, and there is usually more than one vendor available to provide a third-party product.
- The problem is that critical decisions aren't easily reversible.

### Reversibility
- The mistake lies in assuming that any decision is cast in stone - and in not preparing for the contingencies that might arise.
  - Think of them as being written in the sand at the beach.
  - A big wave can come along and wipe them out at any time.

> Tip 18: There are no final decisions.

### Flexible architecture
- While many people try to keep their code flexible, you also need to think about maintaining flexibility in the areas of architecture, deployment, and vendor integration.
- How can you plan for the architectural volatility? You can't
  - What you can do is make it easy to change.
  - Hide third-party APIs behind your own abstraction layers.
  - Break your code into components, even if you end up deploying them on a single massive server.

> Tip 19: Forgo following fads.

- Enable your code to rock-n-roll: to "rock on" when it can, to roll with the punches when it must.

## Topic 12 - Tracer Bullets
- Tracer bullets are loaded at intervals alongside regular ammunition.
  - When they are fired, their phosphorous ignites and leaves a pyrotechnic trail from the gun to the whatever it hit.
  - If the tracers are hitting the target, then so are the regular bullets.
  - Soldiers use these tracer rounds to refine their aim: it's pragmatic, real-time feedback under actual conditions.

- That same principle applies to projects, particularly when you are building something that hasn't been built before.
  - Your users have never seen a system like this before, their requirements may be vague.
  - You may be using algorithms, techniques, languages, or libraries you are not familiar with.
  - The environment you are working in will change before you are done.

### Code that glows in the dark
- Look for something that goes from a requirement to some aspect of the final system quickly, visibly, and repeatably.
  - Look for the important requirements that define the system.
  - Look for areas where you have doubts, and where you see he biggest risks.

>Tip 20: Use tracer bullets to find the target.

- The first tracer bullet can be simply to create the project, add a "hello world!" and make sure it compiles and runs.

- For a system with various layers:
  - Look for a simple feature that allows to exercise them together.
  - Implement only what's needed of that feature to get through all the layers.

- Tracer code is not disposable: you write it for keeps.
  - It contains all the error checking, structuring, documentation, and self-checking that any piece of production code has.
  - Once you have an end-to-end connection among the components of your system, you can check how close to the target you are.
  - Once you are on target, add the rest of the functionality.

- Tracer development is consistent with the idea that a project is never finished.
  - There will always be changes required and functions to add.
  - It is an incremental approach.

- The conventional alternative is to divide the code into modules, which are coded in a vacuum.
  - Modules are combined into subassemblies, which are then further combined, until one day you have a complete application.
  - Only then can the application as a whole be presented to the user and tested.

- Tracer code approach has many advantages:
  - Users get to see something working early.
  - Developers build a structure to work in.
  - You have an integration platform.
  - You have something to demonstrate.
  - You have better feel for progress.

### Tracer bullets don't always hit their target
- Tracer bullets show what you are hitting, which may not be the target.
  - You then adjust the aim until they are on target.

### Tracer code versus prototyping
- With a prototype, you are aiming to explore specific aspects of the final system.
  - You will end up throwing away whatever you lashed together when trying out the concept, and recode it properly using the lesson's learned.
- With tracer code you are aiming to know how the application as a whole hangs together.
- It generates a framework for the users and developers.
- Over time, new functionality and completion is added to this framework.
- The framework stays intact.
- The system will continue to behave the way it did.

## Topic 13 - Prototypes and Post-it Notes
- Prototypes are designed to answer just a few questions.
  - They are much cheaper and faster to develop than applications that go into production.
- If you find yourself in an environment where you cannot give up the details, than you need to ask yourself if you are really building a prototype at all.

### Things to prototype
- Anything that carries a risk
  - Architecture
  - New functionality in an existing system
  - Structure or contents of external data
  - Third-party tools or components
  - Performance issues
  - User interface design

- The value of prototyping does not lie in the code produced, but in the lessons learned.

>Tip 21: Prototype to learn.

### How to user prototypes
- What details can you ignore?
  - Correctness: dummy data for example
  - Completeness: limited functionality
  - Robustness: incomplete or missing error checking
  - Style: not much int the way of comments and documentation

- Prototypes gloss over details, and focus in on specific aspects of the system being considered
  - Consider using a high-level scripting language, as these languages can get out of your way.
  - For UI, use a tool that lets you focus on the appearance and/or interactions without worrying about code or markup.

### Prototyping architecture
- Some specific areas to look for in the architectural prototype:
  - Are the responsibilities of the major areas well defined and appropriate?
  - Are the collaborations between major components well defined?
  - Is coupling minimized?
  - Can you identify potential sources of duplication?
  - Are interface definitions and constraints acceptable?
  - Does every module have an access path to the data it needs during execution? Does it have that access when it needs it?

### How not to use prototypes
- Make sure that everyone understands that it is disposable code.

## Topic 14 - Domain Languages
- The language of the problem domain may also suggest a programming solution.

>Tip 12: Program close to the problem domain.

### Some real-world domain languages
- RSpec: a test in RSpec is intended to reflect the behavior you expect from your code.
- Cucumber: intended to be read by the customers
- Phoenix routes: mapping incoming HTTP requests onto handler functions in the code.
- Ansible: a tool that configures software, typically on a bunch of remote servers. The specification can be written in YAML

### Trade-offs between internal and external languages
- Use off-the-shelf external langauges (such as YAML, JSON, or CSV).

## Topic 15 - Estimating
- By learning to estimate, and by developing this skill to the point where you have an intuitive feel for magnitudes of things, you will be able to determine, at first glance, their feasibility.

>Tip 23: Estimate to avoid surprises

### How accurate is accurate enough?
- The units make a difference in the interpretation of the result.
  - 125 working days versus 25 weeks vs about six months

### Where do estimates come from?
- All estimates are based on models of the problem.
- To get good answers: ask someone who's already done it.

### Understand what's being asked
- The first part of any estimation exercise is building an understanding of what's being asked.

### Build a model of the system
- From the understanding of the question being asked, build a rough-and-ready bare-bones mental model.
- Often, the process of building the model leads to discoveries of underlying patterns and processes that were not apparent on the surface.
- Building the model introduces inaccuracies into the estimating process.
  - Trade off between simplicity and accuracy.

### Break the model into components
- With a model in hand, decompose it into components.
  - Mathematical rules that describe how these components interact.
  - Each component will typically have parameters that affect how it contributes to the overall model.

### Give each parameter a value
- Work out which parameters have the most impact on the result, and concentrate on getting them about right.
- Have a justifiable way of calculating these critical parameters.

### Calculate the answers
- Only the simplest cases will an estimate have a single answer.
- Answers that seem strange may hint that there is a problem in the model.

### Keep track of your estimating process

### Estimating project schedules
- Painting the missile
  - PERT: optimistic, most likely, pessimistic estimates
- Eating the elephant
  - One bite at a time

>Tip 24: Iterate the schedule with the code.

### What to say when asked for an estimate
- "I'll get back to you."
- You almost always get better results if you slow the process down and spend some time going through the steps.
